## 实证结论

这台设备是 **M5StickS3（K150）**，不是 CoreS3。依据是运行中的固件自报 `ESP32-S3`、M5 board enum `26`、`135×240` 屏幕，且其精确构建标识为 `task-pet-0.5-numeric-v2`；在 `D:\reading-pet` 找到与该构建标识、串口协议和 StickS3 启动代码一致的固件源码。

| 项目 | 实证 | 结论 |
|---|---|---|
| Windows 枚举 | `COM10`、ESP USB Serial/JTAG（`VID_303A&PID_1001`） | 与 ESP32-S3 原生 USB 一致 |
| 现有固件 | 被动读取收到 protocol 2 的 `rhythm` 心跳；随后以文档化 `hello_request` 查询 | 现有固件可安全响应串口协议 |
| 显示 | `hello` 返回 `width=135`、`height=240`、`display_ready=true` | 运行时已初始化 StickS3 显示驱动；未从电脑视觉确认实体屏幕内容 |
| 扬声器 | `speaker_query` 返回 `enabled=true`、空闲；一次显式 600ms、音量 `64/255` 的三音测试返回 `started`，随后 `completed=true`、驱动恢复空闲 | 固件已调用音频驱动且软件流程完成；**未证明人耳听到** |
| 震动 | StickS3 官方规格未列内置震动马达 | 本项目不承诺震动反馈 |

设备会话标识、累计互动和其他个人状态没有记录在本文件中。

## 当前固件的边界

现有 `task-pet-0.5-numeric-v2` 是阅读宠物固件：它能显示宠物动画和既定中文界面，也有受确认保护的扬声器测试；但没有“接收任意照片情感回复并展示一行新文案”的串口命令。因此，本轮没有为了改屏幕句子而改写固件。

## 产品含义

项目所需的是基于照片的宠物情感回应，而不是纯传输回执。后续固件应在真实图像判定完成后，使用一页短表情和一句话，例如：

```text
  [短表情]
      “月亮从云边露出来了。”
```

这是产品文案示例，并非本次设备实测回复。用短表情/动画和一句宠物式短话为主；传输中才显示小型状态提示，使它成为 Reachy 的随身回应窗口，而不是状态监控器。

声音可作为可关闭的提醒。软件已完成一次低音量短音测试，但必须由现场人耳确认后才能称为“可听”；本机没有内置震动反馈路线。

## BLE 与 Wi-Fi 可行性

ESP32-S3 平台支持 Wi-Fi station 与已连接 BLE 并发，但共享 2.4GHz 射频并按时分复用。照片接收、热点上传、队列、超时和重连仍需真机验证。这支持后续由 M5 作为眼镜唯一 BLE central、经手机热点上传的无手机屏幕流程。

这不证明当前阅读宠物固件已经实现 BLE、Wi-Fi、Luma GATT client 或照片回应 API。当前项目电脑桥接拥有眼镜连接；M5 不能未经连接切换设计而成为第二个所有者。

## 下一步验证

1. 由 reading-pet 唯一固件负责人按本项目的产品事件协议增加照片回应能力，不在本项目复制维护固件。增加受长度/字符集限制的回应命令，并适配中文字体和小屏排版。
2. 刷写前完整备份 StickS3 8MB flash、核验哈希，并验证该项目已有的恢复路径；不得整片擦除。
3. 只在备份和恢复路径通过后，刷入含“测试”标识的临时版本，显示表情加一句中文，并进行一次低音量提醒音测试。实体屏和人耳均须现场确认。
4. 最终验收：眼镜新拍照片 -> M5 BLE 接收 -> 手机热点上传 -> 陪伴服务产生有图像依据的情感回应 -> M5 显示；随后验证断网和重连。
